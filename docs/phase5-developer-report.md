# Phase 5 ডেভেলপার রিপোর্ট — অ্যাকাউন্টিং, API ও ডেটা ইন্টিগ্রেশন স্ট্যাবিলাইজেশন

## ১. ফেজ ৫-এর লক্ষ্য ও সারসংক্ষেপ
বিস্তারিত অডিটের পর আর্থিক ডেটা-ফ্লো-এর সব জায়গা **একটি শেয়ার্ড অ্যাকাউন্টিং মডেলে** একীভূত করা হয়েছে, এবং ফ্রন্টএন্ড-ব্যাকএন্ড ইন্টিগ্রেশনে ধরা পড়া আসল সমস্যাগুলো ঠিক করা হয়েছে। বড় ফিক্স: (ক) `বাকির খাতা` (dues) শুধু PHP/SQLite-এ ছিল — Node/MySQL-এ কোনো রুটই ছিল না, তাই ফ্রন্টএন্ডের `/api/dues` কল চিরকাল ঝুলত (হ্যাং); (খ) ড্যাশবোর্ডের মাসিক প্রফিট রিপোর্টের সাথে মিলত না (আলাদা ক্যালকুলেশন); (গ) সার্ভারে কোনো ভ্যালিডেশন ছিল না; (ঘ) ট্রানজেকশন ছিল না; (ঙ) ব্যাকআপ/রিসেটে ফেজ ২/৪/৫-এর নতুন ডেটা অনুপস্থিত ছিল। বাকিগুলো পরীক্ষা করে প্রমাণিত হয়েছে ঠিক আছে।

## ২. অডিট রিপোর্ট (ইনস্পেকশন → ম্যাপিং → আইডেন্টিফিকেশন)
- **রুট ম্যাপ:** Node (Express) ১২টি রিসোর্স + PHP (লিগ্যাসি, SQLite)। ডেভ/প্রোডাকশনে Node+MySQL ব্যবহৃত; PHP শুধু লিগ্যাসি প্যারিটির রেফারেন্স।
- **ধরা পড়া আসল সমস্যা (এভিডেন্সসহ):**
  1. `/api/dues` Node-এ নেই, `dues` টেবিল MySQL-এ নেই → ফ্রন্টএন্ড কল হ্যাং (catch-all কোনো রেসপন্স দেয় না)। **ফিক্সড** — ফেজ ৫-এর প্রধান ফিক্স।
  2. Node সার্ভারে কোনো ট্রানজেকশন নেই (grep: zero)। **ফিক্সড**।
  3. income/expense/bkash POST-এ সার্ভার-সাইড ভ্যালিডেশন নেই। **ফিক্সড**।
  4. ড্যাশবোর্ড `date.startsWith(currentMonthPrefix)` দিয়ে মাসিক হিসাব করত → মাসের ১-২ তারিখের এন্ট্রি আগের চক্রের অন্তর্গত (শেয়ার্ড নিয়ম) অথচ ড্যাশবোর্ডে গোটা আগস্ট-চক্রে ঢুকত; রিপোর্টের সাথে অমিল। **ফিক্সড** (শেয়ার্ড মডেল)।
  5. ব্যাকআপ এক্সপোর্টে `expense_categories`, `employee_salaries`, `salary_payments`, `dues`, `users.monthly_salary` নেই; রিসেটেও মুছে না → অরফান ঝুঁকি। **ফিক্সড**।
  6. ব্যাকআপে restore রুট কারো নেই (PHP-তেও নেই) — এক্সপোর্ট+রিসেটই ডিজাইন। **পরিবর্তন করা হয়নি** (ডকুমেন্টেড)।
- **যাচাই করে ঠিক আছে:** (ক) হিসাব চক্র ফাংশন সব জায়গায় একই (accountingPeriod.ts) — ফেজ ৩ ঠিক ছিল; (খ) ExpenseManager-এর ক্যালেন্ডার-মাস ফিল্টার শুধু মেমো/রেজিস্টার ভিউ — আর্থিক গণনায় নয়; (গ) bKashManager-এর মাস ফিল্টার আসল ওয়ালেট-লেজার ডিজাইন — রিপোর্টে পিরিয়ড ব্যবহৃত; (ঘ) কুইক-বক্স লক → ডেটা না থাকায় (COUNT=0) কার্যত অপরিবর্তিত — লজিক ঠিক; (ঙ) ইনডেক্স: সব ডেট টেবিলে `idx_date` আছে, salary টেবিলে কম্পোজিট — নতুন ইনডেক্স লাগেনি (Task 18); (চ) STAFF সার্ভার-সাইডে সব পড়তে পারে — PHP ডিজাইন (UI-লেভেল রেস্ট্রিকশন), সার্ভার সেটা শক্ত করেনি, বেতন API owner-only (ফেজ ৪)।

## ৩. একক অ্যাকাউন্টিং পিরিয়ড সংজ্ঞা (Task 2)
একটি মাত্র ফাংশন সেট — `src/utils/accountingPeriod.ts` (ফ্রন্টএন্ড ও সার্ভার দুটোই import করে): পিরিয়ড `YYYY-MM` = `YYYY-MM-03 .. YYYY-(MM+1)-02`; ১-২ তারিখের এন্ট্রি আগের পিরিয়ডে। ব্যাকএন্ড `server/routes/salary.ts`, `server/routes/financials.ts`-সহ সব জায়গায় ব্যবহৃত। সীমানা টেস্ট (ফেজ ৪ + এবার): 08-02 → 2026-07; 08-03 → 2026-08 ✓।

## ৪. শেয়ার্ড আর্থিক মডেল (Tasks 3/5/7/15) — মূল আর্কিটেকচার পরিবর্তন
নতুন `src/utils/financialModel.ts` — `computePeriodSummary({incomes, expenses, period, settings, salarySnapshot, catIsFixed, maxDate})`। একই ফাংশন এখন তিন জায়গায় একই সংখ্যা দেয়:
- **ReportsManager** (স্মার্ট রিপোর্ট, `maxDate = আজ/চক্রশেষ`),
- **Dashboard** (মাসিক প্রফিট কার্ড, ১-আজ/১-গতকাল কার্ড, ফিক্সড ডিডাকশন কার্ড),
- **ব্যাকএন্ড** `GET /api/financials/summary?period=` (owner-only) — রিপোর্ট/ড্যাশবোর্ড সংখ্যা সার্ভার থেকে যাচাইযোগ্য।

নিয়ম (ফেজ ১-এর ফর্মুলা অটুট): `মোট লাভ = মোট সেবা রাজস্ব − (মোট পরিচালন ব্যয় + স্থায়ী ব্যয়)`; স্থায়ী = প্রতি খাতে `recorded || configured`; পরিচালন = মোট ব্যয় − রেকর্ডেড স্থায়ী; রাজস্ব = `getIncomeSum` (কুইক-বক্স লক মান্য)। ফেজ ৪ বেতন ইন্টিগ্রেশনও ভেতরে: active হলে SALARY রেকর্ড বাদ + obligation যোগ; না হলে লিগ্যাসি।

**যাচাই:** `2026-06` পিরিয়ড (সব আসল ডেটা এখানে): মডেল revenue=10352, expense=10250, fixed=15150, operating=1100, profit=−5898 → সরাসরি SQL-এর সাথে ১০০% মিল ✓। 2026-07/2026-08 চক্রে ০ ডেটা → revenue 0, fixed (config) 16650 ✓। প্রমাণ: আগের পুরনো SALARY ব্যয় (৳8000, 2026-07-01) আসলে **পিরিয়ড 2026-06**-তে (১-২ তারিখের নিয়ম) — সেখানে লিগ্যাসি মোডে সঠিকভাবে গণনা হয়।

## ৫. বাকির খাতা (dues) — Node/MySQL পোর্ট (Task 4, সবচেয়ে গুরুত্বপূর্ণ)
- `db/schema.sql`-এ `dues` টেবিল (PHP/SQLite স্কিমা ১:১); সার্ভার স্টার্টে ইডেমপোটেন্ট।
- নতুন `server/routes/dues.ts`, `server/index.ts`-এ মাউন্ট — কন্ট্রাক্ট `api/dues.php`-এর হুবহু: GET তালিকা (date DESC), POST create (`customerName`/`amount>0`/`date` আবশ্যক), POST `/:id/pay` (ট্রানজেকশনে income INSERT + due DELETE, নোট `বাকি পরিশোধ: <নাম>`), DELETE।
- PHP-এর সাথে প্যারিটি: due-pay-এ bKash লেজার এন্ট্রি হয় না (PHP-তেও হয় না) — **ডকুমেন্টেড লিমিটেশন**, ইচ্ছাকৃত।
- ফেজ ৫ হার্ডনিং: তারিখ ফরম্যাট+ফিউচার-ডেট চেক, paymentMethod whitelist, enteredBy-ফলব্যাক (লগ-ইন ইউজারের নাম)।

## ৬. সার্ভার-সাইড ভ্যালিডেশন (Task 8)
নতুন `server/validation.ts` (isValidDate/isValidTime/isPositiveAmount/resolveEnteredBy) + তিনটি POST রুটে প্রয়োগ:
- **income:** amount>0, তারিখ বৈধ+অ-ভবিষ্যত, সময় HH:MM, serviceType খালি নয়, method ∈ {CASH,BKASH}।
- **expense:** amount>0, তারিখ/সময়, category অবশ্যই expense_categories-এ (is_active) অথবা লিগ্যাসি সেটে।
- **bkash:** amount>0, তারিখ/সময়, type ∈ {IN,OUT,PAYMENT}, fee ≥ 0।
টেস্ট: সব ৪০০ কেস ✓ (আমাউন্ট ০, ভবিষ্যত তারিখ, বেআইনি method/type/category/time/নেগেটিভ ফি, খালি service)।

## ৭. ট্রানজেকশন (Task 20)
- **income + bKash লিংক:** BKASH ইনকামের income INSERT ও bkash_records INSERT এক ট্রানজেকশনে → লেজারে কোনো কাল্পনিক এন্ট্রি যেতে পারে না। টেস্ট: দুটো রেকর্ডই অ্যাটোমিকালি তৈরি ✓।
- **বেতন পরিশোধ:** `SELECT ... FOR UPDATE` দিয়ে obligation রো লক → remaining-চেক ও INSERT এক ট্রানজেকশনে → কনকারেন্ট পেমেন্টে ডাবল-স্পেন্ড অসম্ভব। রিগ্রেশন: 3000+5000 → remaining 0; overpay 400 ✓।
- **due-pay:** income INSERT + due DELETE এক ট্রানজেকশনে (PHP-এর মতো) ✓।

- **স্পর্শ করা হয়নি:** `api/*.php` লিগ্যাসি (কার্যকর রয়ে গেছে), `src/utils/finance.ts`-এর পাবলিক API, ড্যাশবোর্ডের রেন্ডার লেআউট।

## ১৬. চালানোর নির্দেশনা
`npm run dev` (FE :3000) + `npm run dev:server` (API :3001) — সার্ভার স্টার্টে `dues` টেবিল অটো-তৈরি। ডুয়েস UI: ইনকাম পেজের "বাকির খাতা" সেকশন (আগে যা হ্যাং করত, এখন কাজ করে)। রিপোর্ট/ড্যাশবোর্ড সংখ্যা এখন কাঠামোগতভাবে অভিন্ন।
